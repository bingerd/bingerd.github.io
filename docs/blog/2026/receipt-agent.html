Teaching an AI Agent to Read Receipts (and Politely Decline Your Netflix Subscription)

June 2026 · 11 min read

Expense reports are the perfect agent problem, and I'll defend that. The input is a crumpled photo of a receipt and the output is structured data in an ERP system. In between sit a stack of company policy and a human who wants to spend zero minutes on this. Getting it wrong has consequences, because the output is literally money.

This year I worked on an internal innovation project at Xebia: an expense assistant that lives in the company chat. You photograph a receipt, share it with the bot, have a short conversation, and the expense lands in the finance system. Along the way it reads the receipt with a vision model, checks what you're claiming against expense policy, and sometimes (this became my favorite part) has to tell a colleague, kindly, that their streaming subscription is not a business expense.

Two tiers, because chat and agents disagree about state

The architecture splits into two tiers, and the split exists because chat platforms and agent runtimes have opposite opinions about state.

Chat webhooks want a stateless receiver that acknowledges fast and doesn't mind retries. Agents are the opposite, because a multi-turn conversation about correcting a receipt's date is state. So the ingress is a slim stateless proxy on Cloud Run that receives webhooks, and the agent itself, built on Google's Agent Development Kit, runs on Vertex AI Agent Engine, which owns sessions properly. One request through the system looks like this:

    AE->>T: add_pending_expense(receipt)
    T->>T: vision parse: merchant, date, total
    T->>FS: hash check — duplicate?
    AE-->>CR: "€23.50 at that ramen place, right?"
    CR-->>Chat: reply in thread
    Note over U,AE: ...corrections, policy checks...
    U->>Chat: "ok, submit"
    AE->>T: submit_pending_expenses()
    Note over T: before_tool_callback:<br/>explicit confirmation? only then run
    T->>T: POST to finance system

The glue between the tiers is the mapping from chat thread to agent session, kept in Firestore, and this little component needed more engineering than I expected. Chat platforms happily deliver events concurrently, so two messages in a fresh thread can race to create "the" session; per-thread locks fixed that. A Firestore read on every single message also adds latency the user feels, so an LRU cache (500 entries, one-hour TTL) sits in front. What began as "just store the thread ID somewhere" ended up with locks, a cache and an eviction policy. In an agent system, the state handling is where a lot of the boring engineering hides.

Everything runs twice, of course: separate dev and prod projects with the same deployment shape, and CI running lint, type checks and tests before anything ships. The finance-system client also has a mock twin that mimics its API without moving money, which is what lets the whole conversation flow be tested end to end by machines and demoed to stakeholders without anyone accidentally expensing a test ramen dinner.

The agent's hands

The agent's capabilities are a small set of tools around one core object, the pending expense. The tools parse a receipt into one, correct a field, list them, merge several receipts into a single claim, discard one, and finally submit. The vision parsing is the least of it. Gemini reads merchants, dates and totals off photographed receipts (JPEGs, PNGs, PDFs) with very little coaxing. The conversation design around correction mattered far more, because the failure mode to design for is "read it slightly wrong", and then the human needs a frictionless way to say so.

The merge tool earns a special mention because it came straight from watching real behavior. A conference trip produces four receipts that belong on one claim, and the natural human instinct is to dump all four photos into the chat at once. An agent that forced four separate submissions would be correct and infuriating. combine_pending_expenses exists because the tool surface should match how people actually behave rather than how the ERP's data model wishes they would.

Two mechanisms carry the safety load. The first is duplicate detection: every receipt image is hashed and checked against previously submitted hashes per employee. The most likely expense "fraud" is a colleague accidentally sharing the same photo twice, a week apart, and the agent should catch that without anyone getting embarrassed.

The second is the submit gate. Submission to the finance system is the one irreversible action, so it's wrapped in a before_tool_callback that refuses to run unless the user has explicitly confirmed in that conversation. Because the gate lives in code and not in the prompt, the LLM cannot talk itself into submitting.

The model proposes. Deterministic code disposes.

That's the pattern I'd generalize from this whole project. Anything that moves money, deletes data, or emails a human gets a hard gate outside the model's reach. Policy checking is the opposite case and lives in the prompt. The expense rules are a markdown file loaded into the agent's instructions at boot, so finance can edit a document instead of filing a ticket against my code, and the agent explains rejections in natural language, citing the actual rule. Deterministic mappings stay in code too: the translation from expense category to the finance system's ledger accounts is a static table, because a language model should never be creative about which ledger your ramen lands in.

Around the agent sits a small plugin stack that does the unglamorous production work. Uploaded files are persisted as artifacts automatically, a context filter keeps conversation history from dragging irrelevant baggage into each turn, and structured logging captures every step. A reflect-and-retry plugin gives the agent one shot at noticing its own tool-call errors and correcting course before a human sees the failure. None of this would make a feature list, but it's the difference between a bot colleagues use twice and one they keep using.

How do you unit-test a conversation?

Then comes the question that decides whether an agent is a demo or a product. The receipt parser and the tools work, but what about the behavior? Does it warn on a policy violation but still let a human decide? Does it refuse the clearly personal expense? Does it stay polite on the third correction? How do you regression-test that?

Our answer became an evalset of 25 scripted conversations, each a full multi-turn scenario with the receipt attachments, the user's messages, and the expected behavior at each turn. The names read like a policy FAQ: the over-limit dinner that should be flagged but not blocked, the personal subscription that should be declined outright, the receipt older than the claiming window. Each case is a small story with a correct ending, and together they're nine hundred lines of JSON that constitute the agent's behavioral contract.

Grading is rubric-based. A judge model that is deliberately not the model powering the agent scores relevance and helpfulness against a 0.8 threshold. Keeping the judge separate matters, because models grade their own family's phrasing generously and you want the grader to argue with the agent rather than agree with it.

What made the suite livable was VCR-style cassettes. LLM interactions are recorded once and replayed deterministically in CI, keyed by request hash. The hashing matters, because storing full prompts would bloat every cassette and leak receipt contents into test fixtures. Fast tests run without an API key and without flakiness, while the genuinely live tests are marked slow and run when it matters. Change a prompt and you re-record with --record-mode=rewrite. The re-recording is useful in its own right, since its diff says "behavior changed here, was that intended?".

Twenty-five conversations is not many. It's also more behavioral coverage than most agents in production have today, and the discipline of writing them changed the agent's design more than once. Scenarios that were hard to script turned out to be scenarios where nobody had actually decided the intended behavior. The evalset became the place where the team argued about what the agent should do, which is a much better venue for that argument than production.

What the corporation taught the agent

Building agents inside a company adds constraints no framework tutorial mentions, and they shaped real decisions. Receipts are personal data, so storage got deliberate retention tiers. Receipt images live 90 days and then vanish, traces live a month, and observability data lives a year in production, long enough to investigate a disputed expense. Each number is a small negotiation between debuggability and data minimization, decided per data class rather than defaulting to "keep everything forever", which is what happens when nobody decides.

Everything the agent does is traced end to end with OpenTelemetry, because "the AI decided" is not an acceptable answer to a finance department asking why an expense was submitted. Trust, in the end, came through the eval suite. Showing stakeholders 25 named scenarios with pass marks moved more skepticism than any live demo did, I think because a demo shows the happy path once, while an evalset shows you went looking for the unhappy ones.

The expense assistant is in production now. Colleagues photograph receipts, argue briefly with a robot about dates, and get reimbursed. And somewhere in the eval suite, a scripted user tries to expense a personal subscription on every single CI run, and the agent politely declines, as it will on every run from now on. There are worse legacies.

References

  • Google Agent Development Kit (ADK): The framework the expense agent is built with. Its tool abstraction maps cleanly onto the pending-expense operations, and its callback hooks (like before_tool_callback) are what make the code-level submit gate possible: interception points that the model cannot bypass.
  • Vertex AI Agent Engine: Google's managed runtime for deployed agents. It owns sessions and state server-side, which is exactly the part you don't want to reinvent. The two-tier design exists because Agent Engine holds the stateful half while Cloud Run holds the stateless webhook half.
  • Gemini (vision + text): The multimodal model doing the actual work: reading merchants, dates and totals off photographed receipts and holding the correction conversation. Multimodality is what makes this work at all, since the input is an image rather than text.
  • Cloud Firestore: A serverless document database, used for the thread-to-session mapping and duplicate-detection hashes. Chosen because this data is small, keyed lookups dominate, and nobody wants to operate a database for what is essentially a distributed hashmap with persistence.
  • VCR.py: Records HTTP interactions once and replays them in later test runs. Applied to LLM calls, it turns nondeterministic, paid, slow API interactions into deterministic, free, fast test fixtures, which takes care of the biggest practical problem in agent testing: a CI run that flakes and sends you a bill.
  • OpenTelemetry: End-to-end tracing across the proxy, the agent and the tools. In a system that submits expenses, the audit question is 'why did this happen', and spans are the answer that satisfies both engineers and a finance department.
